Feasibility & architecture · read-only client

SponsorBlock for stock YouTube & YT Music on Android

No root, no patched APK: a companion app listens to the stock apps' media sessions, resolves the video ID, fetches segments from the SponsorBlock server the same way the extension does, and skips by sending seekTo() back into the app. The approach is already proven for stock YouTube by a small shipped project; nobody has built it for YT Music yet.

Verdict in three facts

Proven

The stock YouTube app accepts seekTo() from other apps via its MediaSession — two shipped projects do exactly this (Sponsor Skip is active, listed on SponsorBlock's own wiki). Position, title, channel and duration are all readable.

The one hard problem

The MediaSession never exposes the video ID — only title + channel/artist. Every viable design resolves the ID via YouTube search and must guard against matching the wrong video.

Greenfield

No project does this for stock YT Music. Same mechanism should work, and ID resolution is actually more precise there (Innertube music search matches title + artist + album). Empty niche.

Everything below designs the companion app around these three facts. "Read-only" = fetch and skip only; no submissions, votes, or logins.

AppFunctions — sealed at three independent layers

1 · The caller permission is unobtainable. Straight from AOSP core/res/AndroidManifest.xml:

<permission android:name=
    "android.permission.EXECUTE_APP_FUNCTIONS"
    android:protectionLevel="internal|role" />
// no signature match, no user dialog, no adb grant —
// role-holders only

The granting roles (SYSTEM_UI_INTELLIGENCE etc.) are systemOnly, and AssistantRoleBehavior grants it to an assistant-role holder only if isSystemPackageAsUser() passes — so even setting a sideloaded app as your default assistant yields nothing.

2 · No functions to call. As of July 2026 adopters are Google Calendar/Notes/Tasks and Samsung's apps; Gemini controls YouTube via server-side extensions and UI automation instead.

3 · Wrong shape anyway. One-shot request→response RPC; no "now playing" schema, no subscription/eventing. Watch Android 17, but the promised broadening targets providers and OEM agents, not sideloaded callers.

MediaBrowserService — the tantalizing near-miss

YT Music's MusicBrowserService hands Android Auto a queue whose mediaIds embed the real video ID — the one IPC surface where the ID actually exists.

But onGetRoot() follows Google's UAMP PackageValidator pattern: caller package name and APK signing certificate are checked against a baked-in allow-list (Auto, Wear, Assistant, System UI). Everyone else gets a null root → onConnectFailed.

Only root + signature spoofing (LSPosed CorePatch) gets past it, which breaks the no-root constraint. The modern Media3 token path doesn't see YouTube's session either (androidx/media#281) — only legacy getActiveSessions does.

Net effect: the video ID sits one signature check away, and that check is the design boundary that makes the title→ID resolver necessary.

Sources: AOSP manifest, AssistantRoleBehavior, AppFunctions docs, UAMP PackageValidator, YT Music onConnectFailed repro, Pano Scrobbler FAQ.

Ground truth · decompiled the real binary

I decompiled YouTube v21.26.364 and read the session code

Not inference from scrobbler behavior — the actual app. Pulled the APK apart with androguard + jadx (8 dex, ~51k classes), and read the two classes that decide everything: the media-browser service and the session-metadata builder. Both prior claims hold, and one is even more permissive than expected.

Confirmed on-device

The session metadata builder sets title, channel, duration, thumbnail, video width/height — and nothing else. No MEDIA_ID. No MEDIA_URI. The video ID is genuinely absent.

Surprise

YouTube's MediaBrowserService accepts every caller except SystemUI — no signature allow-list at all. But it serves an empty tree, so there's still nothing to harvest.

Also confirmed

The session advertises ACTION_SEEK_TO (flag 256) whenever the video is seekable, and publishes live position — so the skip primitive is real.

1 · The session metadata builder — aqpv.m()

This is the exact method (deobfuscated: tt = MediaMetadataCompat.Builder, .d=putString, .c=putLong, .b=putBitmap). This is everything the phone's now-playing session carries.

2 · The MediaBrowserService — MainAppMediaBrowserService

The whole class is this small. b() is onGetRoot, c() is onLoadChildren (base class cvb, root type cun defaulting to "__EMPTY_ROOT__").

cun b(String callerPackage) {                 // onGetRoot
    if (callerPackage.equals("com.android.systemui")) return null;   // only SystemUI is refused
    return new cun(null);                       // everyone else: root id "__EMPTY_ROOT__"
}

    result.b(Collections.EMPTY_LIST);           // ← always empty. no browsable items, ever

// onCreate's real job: publish the MediaSession token — that's why the service exists

Contrary to the older YT-Music-era finding (third parties got onConnectFailed), the 2026 YouTube app grants a browse root to anyone but hands back an empty library. So the one IPC surface where the video ID could live — queue mediaIds — is empty on this app. Connecting buys you nothing the plain getActiveSessions path doesn't already give.

3 · Seek + position are real

In the same class, the playback-state builder ORs 256 (ACTION_SEEK_TO) into the advertised actions whenever the stream reports seekable, and writes the live position into the state — the two primitives the skip engine needs.

// aqpv — playback state action flags
long actions = playing ? 6 : 0;        // PLAY|PAUSE
if (...) actions |= 16;                 // SKIP_TO_NEXT
if (...) actions |= 32;                 // SKIP_TO_PREVIOUS
if (isSeekable) actions |= 256;        // ACTION_SEEK_TO  ← third-party seekTo() accepted
state.d(playbackState, position, speed);   // live position published

Net: the reverse-engineering confirms the design end-to-end — observe title/channel/duration/position, send seekTo() back — and hard-proves that the missing video ID is a deliberate gap in what YouTube publishes, closable only by the title→ID resolver.

Where the ID does live — in-process (what ReVanced reaches)

The videoId is an obfuscated field on YouTube's PlayerResponseModel and the first String arg of the player-parameter builder. ReVanced can't name it either — it matches by anchor strings:

videoIdFingerprint  → "Failed to download video
                       (IllegalStateException): %s"
timeReference (100ms) → "Media progress reported
                       outside media playback: "

I grepped this exact APK: all three anchor strings are present (classes6 + classes2). So the ID and a 100 ms position tick genuinely exist in the process — just behind the app's own code, reachable only by patching the APK (ReVanced) or the Lounge cast channel (iSponsorBlockTV), never by a stock observer.

YouTube Music — same wall, stricter door

YT Music publishes TITLE / ARTIST / ALBUM / ALBUM_ARTIST / DURATION / ART and a like-state rating — but no MEDIA_ID, no MEDIA_URI, no queue ID, same as the main app.

One difference: its MusicBrowserService.onGetRoot returns null for non-Google-signed callers → onConnectFailed. So where the YouTube app accepts everyone but serves an empty tree, YT Music simply refuses you. Either way, zero IDs. A project built to extract it (Youtube-Music-API-Bridge) concluded it's impossible and pivoted to a browser extension.

Shizuku / dumpsys — no real gain

com.android.shell holds MEDIA_CONTENT_CONTROL (signature|privileged, so not pm grant-able), which lets shell call getActiveSessions(null) without the notification-listener grant.

But it returns the identical MediaController surface — same empty metadata. The only thing Shizuku buys is skipping the scary notification-access prompt. dumpsys shows strictly less. WRITE_SECURE_SETTINGS/DUMP/usage-stats unlock nothing here.

Resolver precision — the honest caveats

Title+channel → ID via search is a best guess, and research surfaced two failure modes beyond re-uploads:

  • ATV vs OMV: a song's Art-Track and Official-Music-Video versions are different video IDs with different SponsorBlock segments — the search may pick the wrong twin.
  • User uploads / private IDs: not findable via search at all — no match, skip disabled.
  • Live: unreliable. Duration cross-check + fail-closed keep these from causing wrong skips.

Combined verdict: the deeper dig doesn't open a new door — it forecloses every one (session extras, queue, notification, YT Music, Shizuku, dumpsys) and explains why the resolver is the only path. It also sharpens the resolver's risk profile (ATV/OMV, user uploads, live), which the validation layer must handle. Sources: anddea/revanced-patches (fingerprints), Pano Scrobbler FAQ, PendingIntent security, ytmusicapi, plus the decompiled aqpv/aqpw/ff/MainAppMediaBrowserService classes.

Exposure map · where the ID goes when it leaves the app

How the app does expose the video ID — and why none of it helps

The ID isn't purely trapped in-process — the app pushes it across boundaries all the time. But every exposure is outbound and initiated by the user or by casting. The two channels that carry the raw 11-char ID only fire when playback moves off the phone to an external device. For a video playing locally, the only reachable channel has no ID. Below: traced in the binary, corroborated by the cast/lounge tooling.

The one green-carrying lane a companion could read (Cast contentId, unauthenticated on LAN port 8009 — how CastSponsorSkip works) only exists while the phone casts to an external device, at which point the phone isn't the thing playing. For local phone playback, you're left with the amber lane: reachable, no ID.

Binary evidence — the app is a sender everywhere

  • Lounge role is fixed: aluk enumerates setVideo/setPlaylist as outgoing commands and nowPlaying as an incoming event — the phone controls a screen, never hosts one.
  • The ID goes out, not in: alyq serializes {"videoId":"…"} into the cast command sent to the TV.
  • DIAL is discovery-only: almz sends the M-SEARCH … urn:dial-multiscreen-org probe — the phone looks for receivers, it doesn't answer.
  • No self-screen: the one registerScreen… hit was registerScreenCaptureCallback — an unrelated Activity API, not a Lounge screen registration.

What this means for the companion

Nothing changes the plan, but it closes the "just tap into casting" idea cleanly: the cast channel is real and carries the true ID, yet it's mutually exclusive with local playback — you can't observe a locally-playing video through it.

So the exposure map collapses to the same two options as before: read title + channel from the local MediaSession and resolve, or require the user to be casting (the iSponsorBlockTV model, which already exists and targets TVs). For "SponsorBlock on the phone screen itself," the resolver is the only road.

The cast-grab idea · evaluated on its merits

Spoof a receiver to capture the exact ID — with the cast tap as the trigger

The idea: run a fake cast receiver, let the user tap Cast → pick it (that gesture is the "fetch segments" trigger), grab the exact videoId it's handed, disconnect, then skip locally. Reframing the manual tap as the intended trigger genuinely removes the automation blocker. Here's what survives — and the one cost that doesn't go away.

What the reframing fixes

  • Automation blocker — gone. You accepted the manual cast as the trigger, so "no app can make YouTube cast" no longer matters.
  • Cert wall — sidestepped. Going DIAL+Lounge (not native Cast) avoids the AUTH_CHALLENGE device-cert that blocks fake Google-Cast receivers outright.
  • The big win — exact ID. You get the true 11-char ID, so the wrong-video / ATV-vs-OMV / user-upload failures of the search resolver simply vanish.

The cost that stays — casting is a handoff

Casting doesn't mirror, it moves the video off the phone. To be handed the ID you must let the video eject to the fake screen (which plays nothing), and on disconnect YouTube stops playback rather than seamlessly resuming — so each trigger is a stop-and-replay, ~3 taps and a few seconds, per video.

Plus two fragilities: the fake screen registers against YouTube's Lounge servers — the same unofficial surface YouTube broke in April 2026 — and a screen that connects then instantly drops is abuse-flag-shaped.

The core capability · skipping (solved)

Once you have the ID + segments: skipping is the easy half

Your pipeline is right — cast-grab is just the per-video fetch trigger; the segments come back from the SponsorBlock server in the background; then the actual skipping happens on the local MediaSession while you watch on the phone. And skipping is the tractable part: I verified all three primitives it needs directly in the YouTube binary, and two shipped apps already do it.

1 · Live position

PlaybackState publishes position + updateTime + speed (fh.d(state, pos, speed)). Extrapolate exact current time between updates: pos + (now − updateTime) × speed.

2 · Seek is honored

YouTube's own callback kwr extends ew overrides onSeekTo() (kwr.g(long)) and routes it to the player. An external transportControls.seekTo() really moves playback.

3 · Seek is offered

The session advertises ACTION_SEEK_TO (flag 256) whenever the video is seekable — so the control is enabled for third-party controllers, not just the system scrubber.

The skip engine — schedule, verify, seek

Not a busy-poll — anchor on each PlaybackState update and schedule one timer to the next segment, re-verifying right before firing so an ad or a manual scrub can't cause a bad skip.

// runs in the companion; `mc` is the MediaController for YouTube's session
onPlaybackStateChanged(s):
    cancelPendingSkip()
    if s.state != PLAYING: return
    pos = s.position + (now() - s.lastPositionUpdateTime) * s.playbackSpeed
    seg = firstEnabledSegmentEndingAfter(pos)          // next auto-skip segment
    if seg == null: return
    if pos >= seg.start:                               // already inside → skip immediately
        mc.transportControls.seekTo(seg.end + EPSILON); return
    scheduleAt((seg.start - pos) / s.playbackSpeed):   // fire when playback reaches it
        p = extrapolate(currentState)
        if playing and abs(p - seg.start) < GUARD:       // re-verify: not an ad shift / user seek
            mc.transportControls.seekTo(seg.end + EPSILON)
        else: onPlaybackStateChanged(currentState)     // re-anchor and reschedule

// re-anchors automatically: YouTube pushes a fresh state on play/pause/seek/speed-change

The next challenge — painting segments on the seekbar

You flagged this correctly as a separate, harder problem. You can't draw inside YouTube's process, so the only no-root route is a two-part hack:

  • AccessibilityService to locate the seekbar node and read its on-screen bounds + the video's total duration.
  • An overlay window (TYPE_APPLICATION_OVERLAY) drawing thin colored marks at x = bounds.left + (segStart/duration) × bounds.width for each segment.

It's fragile — bounds shift on rotation, fullscreen, gesture-hide, and mini-player — so the overlay must re-track on every layout change. Cosmetic only: nothing here affects the skipping.

Suggested order

  • Milestone 1 — skip. Notification-listener → MediaController → the skip engine above. Feed it a hardcoded videoID first, prove seeks land, then wire the real fetch.
  • Milestone 2 — acquire the ID. Start with the silent title→search resolver (zero friction); add the cast-grab as the opt-in exact-ID trigger.
  • Milestone 3 — paint. The accessibility + overlay seekbar tint, last, as polish.

Architecture

One foreground service, five parts. The session listener watches the stock apps' MediaSessions (needs the one-time notification-access grant); the resolver turns title + channel into a video ID; the segment client talks to the SponsorBlock server exactly like the extension; the skip engine sends seekTo() back through the same session — the green arrow is the only "write" the app ever performs.

Video loads → skip fires

The full loop from track change to skip. The Refetch button re-enters at the fetch step with the cache bypassed (the extension's ignoreCache path); pause/resume and speed changes only touch the local scheduling step. On seek or resume, the engine re-checks whether the new position sits inside a segment and skips immediately.

The one hard problem: getting the video ID

YouTube — search scrape

Search youtube.com/results for "title channel", parse the ytInitialData JSON, and accept a result only when both title and channel match exactly (channel comes from METADATA_KEY_ARTIST). Fall back to title-only.

This is what the two shipped prototypes do — Sponsor Skip (title-only, top result) and alex-kuksa's (title+channel exact).

YT Music — Innertube search

The unofficial music.youtube.com/youtubei/v1/search endpoint (the one ytmusicapi wraps) filters to songs and matches title + artist + album + duration — far more precise than scraping, no API key.

YT Music metadata is cleaner too (real artist/album fields, verified via scrobbler projects). This is why the Music side, though unshipped, is arguably easier.

Validation — belt and suspenders

  • Duration cross-check: compare the session's METADATA_KEY_DURATION against the candidate's duration and the videoDuration field SponsorBlock returns per segment. Mismatch beyond ~2 s → discard the match, never seek.
  • Show the match: the now-playing card displays which video was matched, with a "wrong video?" override.
  • Fail closed: no confident ID → no skipping. A wrong skip is worse than no skip.

Why not the official Data API

search.list now has a dedicated quota bucket of 100 calls/day — a normal viewing session exhausts it before lunch. Usable only as an optional user-supplied-key fallback, never the primary path.

Root cause: neither app puts the video ID in MEDIA_ID, the media URI, session extras, or queue items — confirmed by every scrobbler project that ever looked. Title + channel/artist is all you get, so resolution + validation is the design's load-bearing wall.

Risks & honest limitations

  • HighWrong-video match. Title search can resolve to a re-upload or lyric video and skip the wrong seconds. Mitigation is the whole validation panel above: exact title+channel, duration cross-check, fail closed, visible match in UI.
  • MediumSkip precision ~±1 s. Position comes from state snapshots, not a 30 fps clock. Extrapolating with lastPositionUpdateTime × playbackSpeed (which existing prototypes don't do) gets close; a per-device offset absorbs the rest.
  • MediumAds are invisible. The phone MediaSession doesn't flag YouTube ads, so a skip scheduled across an ad break can fire at the wrong content time. Detect via sudden duration/metadata anomalies and re-verify position right before every seek.
  • MediumGoogle can change anything. Metadata fields, seekTo acceptance, search HTML — all unofficial surface. Same fragility every SponsorBlock port lives with (the Lounge API broke pairing for everyone in April 2026).
  • LowShorts. No reliable way to distinguish them; Sponsor Skip debounces anything ≤ ~3 min. Segments on Shorts are rare, so treating short videos conservatively costs little.
  • LowPermission friction & battery. One-time notification-access grant (scary dialog); a foreground service that only wakes while a target session is active keeps battery impact negligible.

Nothing here is a blocker — Sponsor Skip ships with most of these unmitigated and works. The mitigations just decide whether it feels solid or flaky.
